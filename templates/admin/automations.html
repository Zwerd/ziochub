IOC push — HTTP POST (JSON body)

After a new IOC is saved (single submit, API ingest, staging, CSV, TXT), the server POSTs to each enabled target. The request body is built from your Jinja2 template with variable ioc:

  • ioc.type, ioc.value, ioc.analyst, ioc.ticket_id, ioc.comment
  • ioc.expiration_date (ISO or empty), ioc.campaign_id, ioc.tags (list), ioc.tags_json
  • ioc.submission_method, ioc.user_id, ioc.created_at (ISO)

Use {% raw %}{{ ioc.value | tojson }}{% endraw %} for safe JSON strings. Pushes run in the background. IOCs created with analyst = MISP sync user are skipped.

When checked, targets that leave “Verify TLS” unset will not validate server certificates.

POST only. Auth: none, HTTP Basic (user + password), or API key (header name + key).

Test push sends a sample IOC (example.com / Domain) through each target’s template; save not required.

YARA push

Push approved YARA rules to any system that exposes an HTTP(S) API for rule upload (plain body or API-key header, optional delete URL). This is intentionally vendor-neutral: if the remote accepts POSTed rule text and optional removal calls, you can model it here. Optional preset targets from Integrations (e.g. Trellix NX wsapis) are merged with the custom list below when automation runs.

Applies to custom targets here and to optional preset targets tested from Integrations.

OpenDXL

OpenDXL is the open Python client pattern for the DXL message fabric. When enabled, every Hash (MD5/SHA1/SHA256) submitted in ZIoCHub is published to the fabric (e.g. Trellix TIE as Known Malicious). The same stack is used across vendors that ship DXL brokers and client packages — including Trellix (ePO-provisioned clients) and Trend Micro where your deployment exposes OpenDXL-compatible endpoints; follow that vendor’s provisioning docs for certs and broker addresses.

You need both of the following on the Linux server:

  1. Python packages dxlclient and dxltieclient — talk to the DXL fabric and TIE. These are in requirements.txt and install with setup.sh.
  2. Client provisioning package from your management plane — the config file (dxlclient.config) and certificates (e.g. brokercerts.crt, client.crt, client.key). Trellix environments typically provision via ePO; Trend Micro and others use their own flows — without these files the client cannot authenticate to the broker.
Info: Installation and paths on Linux

If you used setup.sh, the DXL Python packages are already installed. Add your vendor’s client package and set the config path below.

1. Python packages (only if missing):
pip install -r requirements.txt or pip install dxlclient dxltieclient

Offline: pip download dxlclient dxltieclient -d ./wheels then on the server: pip install --no-index --find-links ./wheels dxlclient dxltieclient

2. Provisioning: Create or export a DXL client package for Linux from your vendor console (e.g. Trellix ePO: DXL Provisioning / Client Management). Upload each file below, or copy files to the server and enter the config path manually.

Example path: /opt/ziochub/certs/dxl/dxlclient.config — the ZIoCHub process must read this file and the certs it references.
