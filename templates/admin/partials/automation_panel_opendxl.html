When OpenDXL enabled is Yes, ZIoCHub connects to your organization’s DXL fabric (managed by Trellix ePO or an OpenDXL broker) and publishes Hash IOCs (MD5 / SHA1 / SHA256) to Threat Intelligence Exchange (TIE) as Known Malicious file reputation. Managed endpoints that use TIE can then block or score those files. This is not a generic “publish any message to the bus” integration — ZIoCHub uses the documented TIE client API (set_file_reputation) over DXL. Domain, IP, URL, and Email IOCs are not sent on this path.

Requires Python packages dxlclient and dxltieclient on the Linux host (pip install -r requirements.txt). Outbound TCP from the ZIoCHub server to DXL broker hosts (typically port 8883) must be allowed.

How to connect ZIoCHub to the DXL fabric (ePO / OpenDXL)
  1. On ePO (Trellix) — confirm Data Exchange Layer is deployed: DXL brokers are running and the ZIoCHub server can reach them on the network (firewall → broker host:8883). See OpenDXL provisioning overview (ePO-managed fabrics require DXL ePO extensions 4.0+).
  2. Provision a DXL client for Linux — create a new client identity that ZIoCHub will use. Common methods:
    • ePO UI: ePO → Data Exchange Layer → client / provisioning workflow → download the Linux provisioning package (config + certificates).
    • CLI (on a machine with network access to ePO): after installing the OpenDXL Python SDK, run dxlclient provisionconfig <output-dir> <epo-host> <client-name> (default ePO HTTPS port 8443; use -t <port> if different). See OpenDXL CLI provisioning (basic) and provisioning overview.
  3. Authorize the client on the fabric — in ePO, open Server Settings → DXL Topic Authorization and allow this client certificate to send on the TIE reputation-set topic group (documented as TIE Server Set Enterprise Reputation — topic /mcafee/service/tie/file/reputation/set). Without this, Test connection may connect to the broker but fail on TIE set reputation. See OpenDXL authorization overview, managing authorization restrictions, and TieClient.set_file_reputation.
  4. Install Python DXL libraries on the ZIoCHub Linux host — same Python environment as the app: pip install dxlclient dxltieclient (or pip install -r requirements.txt). Offline: download wheels on another host and pip install --no-index --find-links . …
  5. Upload provisioning files below (or copy them manually to data/dxl/ on the server). ZIoCHub stores them with fixed names and rewrites certificate paths inside dxlclient.config to match.
  6. In ZIoCHub: confirm Path to dxlclient.config (auto-filled after config upload), click Test connection — all steps must pass (including a test TIE reputation write), then set OpenDXL enabled to Yes and Save.

Reference: OpenDXL Python SDK · OpenDXL TIE client overview · Update client config (CLI). Internal runbook: docs/DXL_INTEGRATION.md in the ZIoCHub repo.

What to upload — the four provisioning files

These come from the ePO / OpenDXL Linux provisioning package (or from dxlclient provisionconfig). ZIoCHub saves them under data/dxl/ on the server with the names in the right column. You may upload one file at a time or several together; upload the config file last (or again after certs) so the path is set and [Certs] paths are rewritten.

Testing DXL / TIE…
Troubleshooting Test connection
  • DXL libraries fail — install dxlclient / dxltieclient in the same Python venv as Gunicorn, then restart ZIoCHub.
  • Config file not found — path must be on the Linux host; use upload or copy files to data/dxl/ and point to the absolute path.
  • Connect to broker fail — check broker host/port in [Brokers], firewall (TCP 8883), and that broker / client certificates match the ePO CA bundle.
  • TIE set reputation fail (broker OK) — the DXL client is not authorized for TIE reputation writes in ePO; assign the correct OpenDXL permission group to this client’s certificate CN.
  • Hash not appearing in TIE — confirm OpenDXL enabled is Yes after a successful test; only Hash type IOCs are pushed; check server logs and Feed Pulse → Connections for last DXL push telemetry.
