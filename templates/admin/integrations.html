▸ How to create a Cortex XDR API key (Standard or Advanced)
  1. In the Cortex XDR console, open Settings → Configurations → Integrations → API Keys (see Cortex XDR API overview).
  2. Click + New Key. Choose a Security Level - Standard (raw key in Authorization, no signing) or Advanced (HMAC-style signed header). Use the matching value in Security level below; a mismatch always returns HTTP 401.
  3. Create an Advanced API key (required for signed REST calls). Standard keys are not supported by ZIoCHub.
  4. Grant permissions needed for IOC/TIM operations (at minimum: ability to manage indicators / rules; many tenants use a role with Instance Administrator or equivalent IOC edit rights).
  5. Copy the API Key ID and the API Key secret immediately — the secret is shown only once.
  6. On the same screen, note the API base host (FQDN), e.g. https://api-xxxxx.paloaltonetworks.com — paste that into API base URL below (host only, no /public_api/... path).
  7. In ZIoCHub: paste ID + secret, click Save Cortex XDR settings, then Test connection.

IOC REST references: Get Indicators (IOCs) · Insert Simple Indicators (JSON) · Delete Indicators (IOCs). ZIoCHub uses the documented /public_api/v1/indicators/* routes — not the legacy tim_* aliases (which modern tenants reject with HTTP 403 Invalid API).

If Test shows HTML 500 (not JSON): usually Gunicorn worker timeout while waiting for Cortex (fix: start.sh --timeout 120, systemctl restart ziochub, Ctrl+F5). Use Check module first — must return JSON. Also fix API base URL: no spaces (e.g. not https:// api-…).

▸ How to set up Google SecOps for ZIoCHub (Data Table + service account)

Complete these steps with your Google SecOps / GCP administrator before enabling outbound push. ZIoCHub only needs a pre-created Data Table, a service account JSON key, and the resource identifiers listed in the form below.

Part A — Create the IOC Data Table in SecOps

  1. In the Google SecOps console, open the area where Data Tables are managed (reference / lookup tables for Search and detection). See Google’s Data Table documentation.
  2. Create a new table (suggested id/name: ziochub_iocs or similar). Note the Data table ID — the resource id used in API paths (dataTables/{id}), not only the display title.
  3. Define exactly two string columns, in this order: Column 1 = indicator type slug, Column 2 = indicator value. Example row: domain, evil.example.com.
  4. After the table exists, plan how analysts will use it in SecOps Search / YARA-L (join table values to UDM events). ZIoCHub only maintains the rows; hunt logic is configured in SecOps.

Part B — Collect SecOps and GCP identifiers

  1. In SecOps, open Settings → Profile (or equivalent) and copy the Customer ID (UUID) → paste into Customer ID below.
  2. In GCP, open the project linked to your SecOps instance. Copy the Project number (numeric, not Project ID) → GCP project number.
  3. Note the SecOps region (e.g. me-west1, europe-west4) → Location. ZIoCHub can derive the Chronicle REST host as https://<location>-chronicle.googleapis.com, or paste the full host from the REST endpoints table into Chronicle REST API host.
  4. If your tenant uses a separate Instance ID (UUID) distinct from Customer ID, paste it into Instance ID; otherwise leave empty and Customer ID is used in the API path.
  5. Paste the Data Table resource id from Part A into Data table ID.

Part C — Create a GCP service account and grant access

  1. In GCP Console → IAM & Admin → Service Accounts, create a dedicated account (e.g. ziochub-secops-push@…).
  2. Keys → Add key → Create new key → JSON. Download once and store securely. Paste the full JSON into Service account JSON below (or deliver via your secrets process).
  3. Grant IAM on the Chronicle instance / Data Table. Minimum permissions ZIoCHub uses:
    • chronicle.dataTables.get — Test connection + verify table exists
    • chronicle.dataTableRows.bulkCreate — push new IOC rows
    • chronicle.dataTableRows.list — find rows to remove
    • chronicle.dataTableRows.delete — remove rows on analyst delete / expiry
    A custom role with these four permissions on the instance or table resource is sufficient.
  4. No Domain-wide delegation is required. ZIoCHub requests OAuth scopes https://www.googleapis.com/auth/chronicle (production push) and https://www.googleapis.com/auth/malachite-ingestion (optional diagnostics only).

Part D — Configure and verify in ZIoCHub

  1. Paste all values into the form below. Leave Ingestion API host empty unless you want the optional ingestion probe during tests (not used for IOC push).
  2. Set Enable Google SecOps outbound to Yes only after tests pass.
  3. Click Save Google SecOps settings.
  4. Click Check module (import OK) → Check config (fields + JSON valid) → Test connection (OAuth + GET Data Table).
  5. Enable Include push/remove test row and run Test again to confirm bulkCreate and delete IAM (writes one temporary *.invalid row, then removes it).
  6. Submit a test IOC in ZIoCHub and confirm a new row appears in the SecOps Data Table; delete the IOC and confirm the row is removed.

Field mapping summary: Customer ID + Location + GCP project number + Data table ID build the API parent path projects/{number}/locations/{loc}/instances/{id}/dataTables/{table}. Service account JSON authenticates all REST calls.

HTTP 403 on data_table or roundtrip_create: fix IAM on the table resource. HTTP 401 on OAuth: invalid or revoked JSON key. On the server: python scripts/test_google_secops_setup.py --roundtrip. After code deploy, restart ziochub and hard-refresh the browser (Ctrl+F5) if this panel looks outdated.

▸ Why Data Tables, and how this integration works

Why a Data Table (and not log ingestion)? ZIoCHub does not send IOCs through the Chronicle Ingestion API (malachite-ingestion). Ingestion is for shipping raw log/event payloads into the platform. Our goal is different: make every ZIoCHub IOC a first-class reference dataset inside SecOps that analysts can use while hunting.

In Google SecOps, a Data Table is a managed lookup table tied to your Chronicle instance. Once ZIoCHub writes a row (type + value), SecOps can join that table to UDM events in Search, dashboards, and detection logic. Practically: when TI publishes evil.example.com, analysts can pivot from the table to find matching traffic, DNS, proxy, or auth events in stored logs — without maintaining a separate IOC spreadsheet or manual list. Removing the row on revoke keeps hunts aligned with ZIoCHub (stale indicators drop out of correlation).

End-to-end flow in ZIoCHub

  1. Analyst submits, reactivates, or deletes an IOC in ZIoCHub (GUI or API).
  2. schedule_auxiliary_vendor_integrations queues a background job with the IOC context (type, value, action=create|remove).
  3. ZIoCHub loads the GCP service account JSON, requests an OAuth token (scopes https://www.googleapis.com/auth/chronicle + optional malachite-ingestion for diagnostics only).
  4. Create: POST …/v1beta/{parent}/dataTableRows:bulkCreate with one row: ["domain", "evil.example.com"] (column 1 = type slug, column 2 = value).
  5. Remove: GET …/dataTableRows?filter=<value>, match type+value, then DELETE each row resource (manual delete in Search UI and TTL expiry both trigger remove).

Table shape (required before enabling push)

  • Create the Data Table in SecOps (UI or API) with two string columns, in order: (1) indicator type slug, (2) indicator value.
  • Type slugs ZIoCHub writes: ip, domain, url, hash, email, yara.
  • Enter the table’s resource id (dataTables/{id}) in Data table ID below — not the human-readable title.

API references: bulkCreate rows · list rows · REST endpoints by region.
