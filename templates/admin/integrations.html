Trellix EX / CMS / NX

Email Security (EX), CMS (central manager for EX), and Network Security (NX) are grouped here. Use the buttons below to switch.

Email Security (EX)

Push approved YARA rules to Trellix Email Security (EX): JSON password login to /login/login, then multipart/form-data POST (default upload path /ex/yara_rules_ng/upload_yara). Network Security (NX) web YARA uses /wmps/yara_rules_ng/upload_yara - configure that under Network (NX) with API style wmps. On ZIoCHub YARA delete, matching delete_yara_files POSTs run when the integration is enabled. Fields: yara_file, f_type, content_type.

If you already have a session cookie from the browser, paste it into Manual Cookie to skip login. Otherwise set username and password (EX validates against local/LDAP per appliance). ZIoCHub runs GET then JSON POST on the login path with auth_method password, ldap, or auto (tries password then ldap). For LDAP-backed EX, use auto or ldap and the same username format you use in the web UI (UPN or DOMAIN\user). Default login path /login/login; upload /ex/yara_rules_ng/upload_yara. Optional: CSRF token from DevTools if upload still returns HTTP 203.

One row per appliance (host, paths, credentials or manual cookie). Leave password empty when saving to keep the stored password for that row.

Test uses saved targets and enable flag (save after editing).

Trellix CMS (central manager)

Push approved YARA rules through the CMS web API (/cms/yara_rules_ng/...), not the direct EX path (/ex/...). Use the CMS appliance hostname as base URL. Session login uses the same JSON flow as EX (/login/login by default).

Most CMS deployments require a sensor ID (from DevTools on the YARA page: s_s[sensor] in get_yara_files). Optional: sensor group (All) and sensor rule list names (comma-separated, maps to s_s[s_r_l][]). Do not point CMS targets at the EX integration tab.

One row per CMS host. Leave password empty when saving to keep the stored password.

Test uses saved targets and enable flag (save after editing).

Network Security (NX)

Per appliance: wsapis = REST API key targets (same as Automations YARA push). wmps = browser session to /login/login, then multipart upload to /wmps/yara_rules_ng/upload_yara with f_type=txt and content_type=base (delete uses files[0][type]=txt).

Appliance HTTPS root and wsapis version. Paths follow Trellix docs (add/remove; remove uses POST). These rows are expanded to generic HTTP targets and merged with your custom YARA list under Automations → YARA push when automation runs.

Used for NX tests here and for YARA pushes (same setting as on Automations → YARA push).

wmps test uses saved targets (save after editing). wsapis test uses the current form rows.

Cisco ESA - content dictionary sync

ZIoCHub logs in to the appliance, then adds or removes dictionary words automatically when analysts submit or revoke IOCs (and on expiry if enabled). You only set the API URL, credentials, TLS option, and which dictionary on the ESA maps to which IOC type.

Supported IOC types for ESA: Email, Domain, IP, URL - each row is one dictionary name (exactly as shown on the ESA) and one type. Other IOC types (e.g. Hash) are not sent to ESA.

No trailing slash. Must include /esa/api/v2.0 (or your appliance’s API root).

Must match the Secure Email API Guide for your deployment. Dictionary add/remove and “Test connection” use the same query string.

Required for Group mode (group_name query parameter).

Required for Machine mode (host_name query parameter).

Requires cleaner.py / systemd timer against the same database. If removal fails, the IOC is still deleted locally; check logs.

Use the exact dictionary name from the ESA UI. One IOC type per row; add multiple rows if you use several dictionaries.

Cortex XDR

Uses the documented Cortex XDR Platform API (same host as https://api-…paloaltonetworks.com): IOC management via indicators/insert_jsons (push) and indicators/delete (revoke), and for Hash IOCs only, optional Action Center file block list (hash_exceptions/blocklist). When Enable is Yes, outbound IOC events call cortex_xdr_push_ioc_from_context in the background. Supported types on push: Domain, IP, Hash (URL/Email are skipped).

How to create a Cortex XDR API key (Standard or Advanced)
  1. In the Cortex XDR console, open Settings → Configurations → Integrations → API Keys (see Cortex XDR API overview).
  2. Click + New Key. Choose a Security Level - Standard (raw key in Authorization, no signing) or Advanced (HMAC-style signed header). Use the matching value in Security level below; a mismatch always returns HTTP 401.
  3. Create an Advanced API key (required for signed REST calls). Standard keys are not supported by ZIoCHub.
  4. Grant permissions needed for IOC/TIM operations (at minimum: ability to manage indicators / rules; many tenants use a role with Instance Administrator or equivalent IOC edit rights).
  5. Copy the API Key ID and the API Key secret immediately — the secret is shown only once.
  6. On the same screen, note the API base host (FQDN), e.g. https://api-xxxxx.paloaltonetworks.com — paste that into API base URL below (host only, no /public_api/... path).
  7. In ZIoCHub: paste ID + secret, click Save Cortex XDR settings, then Test connection.

IOC REST references: Get Indicators (IOCs) · Insert Simple Indicators (JSON) · Delete Indicators (IOCs). ZIoCHub uses the documented /public_api/v1/indicators/* routes — not the legacy tim_* aliases (which modern tenants reject with HTTP 403 Invalid API).

If Test shows HTML 500 (not JSON): usually Gunicorn worker timeout while waiting for Cortex (fix: start.sh --timeout 120, systemctl restart ziochub, Ctrl+F5). Use Check module first — must return JSON. Also fix API base URL: no spaces (e.g. not https:// api-…).

Shown in Feed Pulse → Connections → Push state. Leave empty for default label.

HTTPS FQDN only (from API Keys screen), no spaces. ZIoCHub appends /public_api/v1 automatically.

Numeric/string ID from Cortex → API Keys (pairs with the secret below).

API key secret (shown once when the key is created). Leave blank on Save to keep the stored secret.

Must match the value chosen for this API key in Cortex (Settings → Configurations → API Keys → Security Level). A mismatch returns HTTP 401 even if the ID + secret are correct. Advanced also requires the server clock to be within ~30s of UTC.

Requires Cortex outbound enabled. Adds to block list after TIM succeeds; removes on revoke. Public API path hash_exceptions/blocklist.

Google SecOps (Chronicle SIEM)

Outbound IOCs are written to a Google SecOps Data Table via Chronicle REST v1beta (dataTableRows:bulkCreate / list+delete on remove). Create a table with two string columns in order: indicator type slug, then value (e.g. domain, zwerd.com). Service account needs IAM such as chronicle.dataTableRows.bulkCreate and OAuth scopes https://www.googleapis.com/auth/chronicle plus malachite-ingestion (for the optional ingestion probe below).

Shown in Feed Pulse → Connections → Push state. Leave empty for default label.

From Google REST endpoints. If empty, host defaults to https://<location>-chronicle.googleapis.com when Location is set.

If empty, Customer ID is used as the Chronicle instance id in the resource path.

Resource id of the pre-created Data Table (the dataTables/{id} segment), not the display title.

Used only for Test connection (GET /v2/logtypes). Leave empty for default US ingestion host.

Test uses saved settings: validates OAuth, then GET the Data Table if configured, then ingestion logtypes.
